# W3 — channels and ask_user

## 1. Channel HTTP redirect + private-network (SSRF) guard — done

`crates/seagent-channel/src/http.rs` now disables ureq's automatic redirects and follows
them by hand, vetting every hop with the shared `seagent-security::url_safety` rules
(same classification as `seagent-media/src/http.rs`):

- `Http::call` trusts only the origin the call starts at (the operator-configured channel
  base URL), so self-hosted Mattermost/Matrix/Nextcloud/ClickClack/etc. keep working.
  A redirect to any *other* private host is refused before connecting; cloud-metadata
  addresses are refused even when they are the initial target. Cross-origin redirects
  drop the caller's headers (bot/admin tokens) and 301/302/303 switch to a bodyless GET.
- `get_bytes` is now strict (public targets only; used for Discord CDN attachments and
  other remote media). `get_bytes_trusted(url, …, base)` is the explicit form for a
  channel's own configured origin.
- Updated the self-hosted media paths to the trusted form: Telegram (self-hosted Bot API),
  Mattermost, Nextcloud Talk (WebDAV + public share), ntfy, WhatsApp bridge, Signal
  container, BlueBubbles, Google Chat, LINE data API, Matrix, ClickClack, Feishu.
- `Http::call_once` was added for callers that read 3xx themselves; the NIP-05 resolver
  uses it and keeps refusing redirects.
- `agent()` now starts with `max_redirects(0)`, so the direct paths (Telegram POST,
  Nostr) cannot silently inherit redirects either.

Tests (`crates/seagent-channel/src/http.rs::tests`):
`call_allows_the_configured_private_origin_but_blocks_redirects_to_other_private_hosts`,
`get_bytes_is_strict_and_the_trusted_form_allows_only_its_own_origin`.
Unit tests point channels at loopback fakes; a test-only thread-local allowance keeps
those tests working while `block_private_for_test()` restores the real rule for the
security tests. It is compiled out of production.

## 2. Feishu card actions in an unknown chat — done

`crates/seagent-channel/src/feishu.rs` `card_inbound` now returns `None` when the chat
type was never seen instead of defaulting to `ChatType::Group`. Updated/added assertions
in `parses_every_message_kind_mentions_threads_and_callbacks`: a card action in an
unknown chat is refused, an explicitly known chat still passes.

## 3. Slack `list-pins` honours `limit` — done

`crates/seagent-channel/src/slack_actions.rs` parses `limit` (bounded by the existing
`RESULT_LIMIT`) and applies it to the returned pins. Test
`reactions_read_and_pins` now requests `limit: 1` and asserts one pin.

## 4. Teams proactive DM without a prior inbound — done

`crates/seagent-channel/src/msteams.rs`: the configured `tenant` is now authoritative
for `POST /v3/conversations`; the tenant learned from an inbound activity is only the
fallback when config leaves it unset. This makes proactive approval DMs work for users
who never messaged the bot. Added
`proactive_dm_uses_the_configured_tenant_without_any_inbound`; adjusted the old test to
the new precedence. The configured `service_url` was already used for the create call.

## 5. `ask_user` multiple-choice options — done

- `crates/seagent-core/src/tool.rs`: `ToolHost::ask_user_choice(question, choices, multi)`
  with a numbered-list default for plain hosts.
- `crates/seagent-kernel/src/kernel.rs`: the kernel host routes choices through
  `Approver::clarify`, so the existing question objects (choices + multi) reach channel
  surfaces; the answer is mapped back to the option label (multi answers joined).
- `crates/seagent-tools/src/agent.rs`: `ask_user` accepts `options`/`choices` (2–12,
  distinct, non-empty) and `multi_select`/`multiSelect`/`multiple`, validates them, and
  maps a numeric/label reply back to the choice. Free text still works as “Other”.
- `crates/seagent/src/ext.rs`: `PendingItem::Question` is now forwarded to the session's
  chat. Channels with buttons get `ask:<id>:<n>` buttons; all others get the numbered
  text. Button presses answer only in a chat the question was sent to; a typed reply in
  that chat is the fallback. Both go through `approver::answer_by` (audited).

Tests: `ask_user_options_render_a_numbered_fallback_and_map_the_answer`,
`ask_user_rejects_bad_options`, `ask_user_paths` (tools);
`host_ask_user_choice_uses_clarify_and_returns_the_mapped_option` (kernel);
`ask_user_choice_buttons_and_typed_replies_answer_the_question`,
`ask_user_choice_typed_reply_is_the_fallback_without_buttons` (ext).

Left as a limitation: multi-select questions fall back to the numbered text list on
every channel (no multi-press button card), and `ask_user` remains a single question
(the separate `clarify` tool already supports batches).

## 6. Runner-up items — partial / checked

- **Channel `/fork` — partial (working first slice).** `crates/seagent/src/ext.rs`
  intercepts `/fork [title]` in a channel: it branches the current session, opens a
  sibling thread/topic, binds the new session to it, posts a literal recap there, and
  leaves the parent chat/session untouched. Works for channels advertising
  `thread-create` (Discord; Slack now implements it by posting an anchor message and
  returning its `ts`) or `topic-create` (Telegram). Refuses while a turn is running and
  for `/fork --at N` (which keeps `/branch` semantics). Test:
  `channel_fork_creates_a_sibling_thread_and_keeps_the_parent_chat`.
  Left: channels with no thread/topic action (e.g. Feishu cards, Matrix threads) fall
  back to the old `/branch` path; Slack’s thread is anchored on a new message rather
  than an existing one.
- **Teams allowlist reload — no gap found.** `msteams.rs` has no per-account allowlist
  cache; access policy lives in the router/config and is rebuilt from config. No change.
- **Matrix cached credentials — no gap found.** `matrix.rs` persists `next_batch`,
  `device_id` and E2EE state, but never an access token; a password login token lives
  only in memory. Removing an account therefore leaves no cached credential to forget.
